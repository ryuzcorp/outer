title: D1 guide
description: App data in D1 — migrations apply on deploy, tables in code still work.
---

The template ships with D1 **on by default**: `void.config.ts` declares
it, and `pages/index.server.ts` is the pattern to copy — a loader that
reads D1 and one action (an `intent` field tells the forms apart) that
writes it.
## 1. The binding (already declared)

`void.config.ts` ships the database; Outer provisions it on first
deploy. Edits need `bun run build` — bindings are read from the built
config:

```ts
d1_databases: [{ binding: "DB", database_name: "app-db" }],
```

The built `dist/wrangler.json` then carries the binding through Outer's
deploy validation to celld, which creates the database on first use.
celld keys the database by name, so a typo opens a silent empty database
— double-check the name.

## 2. Migrations (schema changes ride the deploy)

Iterate locally with `void db push` (applies the schema without migration
files), then `void db generate` to write `db/migrations/*.sql` and commit
them. `void db migrate` applies pending migrations to the **local**
database only.

On deploy, Outer applies the committed files after the moderation gate,
before the new version serves traffic:

- For an app with a live version, migrations run **before** the upload:
  the fleet adopts a new deploy on its own poll, so uploading first would
  let it serve new code against the old schema. The old code keeps serving
  during the migration, and a migrate failure uploads nothing — the
  previous version keeps serving with certainty.
- A first deploy uploads first and migrates after: nothing serves yet, so
  there is no race. (One caveat: the fleet starts after the upload, so a
  fast first wake could serve new code before its migrations finish.)
- The step runs only when the built config declares `d1_databases` **and**
   the repo holds migration files (`db/migrations/` is the conventional
   dir; the build stages them for celld). No files → the step is skipped.
- Files apply in numeric-prefix order under the app's scoped storage
   credentials; already-applied files are skipped, never re-applied.
- A file edited **after** it was applied fails the deploy — write a new
   migration instead of editing an applied one.
- A failing migration fails the deploy: the previous version keeps
   serving, the log tail carries celld's error, and the message names the
   file.
 
 Seed data counts as page text: no strong profanity in `INSERT`s — the
 pre-live gate reads SQL string literals and a profane seed blocks the
 deploy.
 
 Expand first, contract later: the migration runs while the previous
 version still serves, so prefer additive changes (new tables, new
 nullable columns). A deploy that drops a column the live code still
 reads will serve errors until the new version takes over.

## 3. Tables in code (the starter pattern, still supported)

Apps with no migration files skip the migrate step, so creating tables
where you use them keeps working — as the starter page does:

```ts
import { env } from "cloudflare:workers";

async function database() {
  await env.DB.prepare(
    "CREATE TABLE IF NOT EXISTS item (id INTEGER PRIMARY KEY AUTOINCREMENT, text TEXT NOT NULL)",
  ).run();
  return env.DB;
}

export const loader = defineHandler(async () => {
  const db = await database();
  const { results } = await db
    .prepare("SELECT id, text FROM item ORDER BY id")
    .all();
  return { items: results ?? [] };
});
```

`prepare()` takes exactly one statement; `bind(...)` fills `?`
placeholders; `all()` returns `{ results }`, `first()` one row, `run()`
writes:

```ts
await db.prepare("INSERT INTO item (text) VALUES (?)").bind(text).run();
await db.prepare("DELETE FROM item WHERE id = ?").bind(id).run();
```

Seed data counts as page text: no strong profanity in `INSERT`s — the
pre-live gate reads SQL string literals and a profane seed blocks the
deploy.

## 4. Drizzle, locally

Void's documented query layer is Drizzle: tables in `db/schema.ts` with
helpers from `void/schema-d1`, imported through the `@schema` alias, and
queries through `db` from `void/db`:

```ts
// db/schema.ts
import { integer, sqliteTable, text } from "void/schema-d1";

export const items = sqliteTable("items", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  label: text("label").notNull(),
});
```

```ts
import { items } from "@schema";
import { db, eq } from "void/db";

const all = await db.select().from(items);
await db.insert(items).values({ label: "Milk" });
await db.delete(items).where(eq(items.id, 1));
```

Iterate locally with `void db push` while prototyping, then `void db
generate` before deploying so the schema change ships as a migration file
(§2). The template itself uses raw `prepare`/`bind` for its starter table,
which keeps working with no migration files at all.
